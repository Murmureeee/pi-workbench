Technical Design · v1.0

把 pi 的一次运行拆成可观察、可审批、可回滚、可重放的服务

2026-10-31 范围基线更新完整产品范围、阶段和进度以全量需求清单及全量产品规划为准。本文保留 M0–M5 技术草案，M6–M7 扩展完整本地工作台，M8 为可选候选。旧文关于同目录并行、授权撤销、轮次、快照保留和会话组织按 D01–D15 产品决定细化；M2 的首次发送、无项目会话与归属 / 目录边界见会话与项目设计。技术描述不代表已经实现。

本方案回答“怎么建”：以 pi SDK 子进程为内核，一个本地守护进程统一提供会话、事件、审批、变更与终端能力；Electron 与浏览器共用同一套前端与服务契约。产品行为以 交互式 PRD 为准，本文只做实现决策，不重复需求。

01

文档定位与约束

PRD 定义“用户看到什么、系统必须怎么响应”；本文定义“用什么结构实现、如何验证、按什么顺序交付”。两者共享同一套对象名与状态名，任何冲突以 PRD 的产品行为为准。

维度交互式 PRD本文（技术设计）
回答的问题谁在什么条件下看到什么、可以做什么进程如何划分、数据存在哪里、协议长什么样
约束力功能范围、状态机、审批与回滚规则模块边界、接口契约、性能与安全底线
不包含框架、数据库、端点、代码结构产品文案、交互细节、视觉规范
变更方式产品决策变更 → 更新 PRD 并同步本文影响面实现方案变更 → 新增或修订 ADR

已确认的输入事实

  • pi 定位：包装现有 pi 运行时（pi SDK；用户自装 CLI 仅作兼容后备），产品负责可视化、编排与交互层，不重新实现 agent 循环。
  • 形态：本地优先；Electron 内置运行时，浏览器通过本机守护进程访问同一套服务；单用户。
  • P0：会话与流式对话、工具调用可视化与审批、文件变更与 Diff、终端 / 任务编排 / 配置。
  • 协议事实：SDK 提供 createAgentSession()、session.subscribe()、prompt / steer / followUp / abort 等类型化接口；扩展用 pi.on("tool_call") 在执行前拿到 { toolCallId, toolName, input } 并返回 { block, reason }。父子进程之间不使用文本行协议。
  • 已安装版本：本机 @earendil-works/pi-coding-agent@1.4.0。本文以 1.4.x 的 SDK 类型与事件形状为准，适配层不假设未来版本兼容。

02

系统拓扑与部署

四层结构：外壳只负责呈现与系统集成；daemon 是唯一可信的服务边界；每个活跃会话对应一个 pi 子进程；工作区文件与账本分离存放，互不污染。

部署形态

形态启动方式服务地址说明
桌面（默认）Electron 启动 → 拉起 sidecar daemon → 等健康检查 → 载入 SPA随机端口，仅 127.0.0.1用户无感；退出时 daemon 收到 SIGTERM 优雅关闭
Web（本机）piw serve --workspace <path>默认 4319，可配置浏览器访问；首次配对需要一次性令牌
开发pnpm dev：Vite 5173 + daemon 4319 + 假内核跨端口，Vite 代理默认可切换到真实 SDK 子进程
进程与端口约定 daemon 只绑定回环地址；端口为 0 时由系统分配并写入 ~/.pi-workbench/daemon.json（含 pid、port、startedAt）。Electron 与浏览器都通过该文件发现实例，避免端口冲突与“打开了错误的实例”。

为什么不是“渲染进程直连 pi”

渲染进程直连会带来三个无法收敛的问题：一是 Node 能力暴露给不可信页面；二是多个窗口无法共享同一会话的事件顺序；三是无法在浏览器形态复用。分层后，daemon 成为唯一的事件排序者与审批裁决者，窗口只是订阅者。

03

架构决策记录（ADR）

每条 ADR 只回答一个不可逆或高代价的选择。状态均为“已接受”；修订时在条目内标注修订日期，触及不可逆取舍时另立新 ADR 并注明取代关系。

ADR-001内核 = 每会话一个 Node 子进程，进程内跑 SDK，父子走结构化 IPCAccepted

daemon 为每个活跃会话 fork 一个 Node 子进程；子进程内用 @earendil-works/pi-coding-agent@1.4.0 的 createAgentSession() 运行 agent 循环，父子之间只传类型化的命令、响应与事件对象。审批由子进程内的执行入口守卫，对所有钩子处理后的最终参数快照等待一次裁决。CLI 的 RpcClient 仅作为“用户自装 pi”的兼容后备，不是默认路径。

理由
  • 保留进程隔离：单个会话崩溃不拖垮其他会话与 daemon
  • 没有文本行协议：无需按 \n 切分、无需处理 U+2028 / U+2029，消息按对象原子送达
  • 类型即契约：命令与事件直接复用 SDK 的 d.ts，升级差异由编译器与契约测试暴露
  • 审批钩子在本进程异步等待，不需要 extension_ui_request / response 跨进程往返
  • SDK 为纯 JS / WASM，无原生 ABI，桌面与 Web 用同一份依赖
代价
  • 需维护子进程入口与 IPC schema
  • 与 SDK 版本强耦合，升级必须重跑契约测试
  • 第三方扩展的 ctx.ui 在 P0 不通，只支持自有审批钩子
备选与否决
  • pi --mode rpc + JSONL：CLI 参数与版本漂移、文本解析、打包可执行文件成本更高
  • SDK 直接跑在 daemon：一次崩溃波及全部会话与服务
  • 单进程多会话：无法回收与隔离，审批等待还会挤占事件循环
ADR-002单守护进程 + 双外壳Accepted

daemon 是唯一的业务与数据写入方；Electron 主进程退化为 supervisor，浏览器只是另一个客户端。

理由
  • 同一会话可被多窗口同时观察
  • Web 形态不需要重新实现业务
  • 审批、审计、账本只有一处裁决点
代价
  • 多一个进程与一次握手
  • 需要处理 daemon 崩溃与重启
  • 需严格校验来源，防止本机其他页面调用
备选与否决
  • Electron 主进程承载业务 + 浏览器另写一套服务：两份状态机必然分叉
  • 纯 Web（无 Electron）：无法满足本地文件、PTY、系统集成
ADR-003REST 快照 + WS 增量 + 序号重放Accepted

读模型走 REST 获取一致快照；实时走 WS 推送带 seq 的事件；断线后按 since=seq 重放，缺口过大则重新拉快照。

理由
  • 快照可缓存、可分页，避免一次性传全量历史
  • seq 让客户端能检测丢事件并自愈
  • WS 只承载增量，消息体小
代价
  • 需维护环形事件缓冲（默认 2000 条/会话）
  • 快照与增量的合并逻辑必须幂等
备选与否决
  • 纯 WS：首次连接传输过大，且断线后无法续传
  • 纯轮询：流式 token 的延迟不可接受
ADR-004三类数据各自有唯一事实源Accepted

消息与分支以 pi session JSONL 为事实源；工作台对象（会话索引、审批、授权、变更集、任务、审计）存 SQLite；文件变更以 shadow git 账本为事实源。三者通过稳定 ID 关联，不做双向同步。

理由
  • 不复制 pi 的消息模型，升级时不被卡死
  • SQLite 只存“工作台自己的东西”，可随时重建
  • 账本与业务库解耦，回滚不依赖数据库事务
代价
  • 跨源查询需要 join 逻辑
  • JSONL 解析失败时要降级为只读历史
备选与否决
  • 消息全量镜像进 SQLite：双写不一致，且丢失 entry 树结构
  • 变更集只存 diff 文本：无法可靠回滚
ADR-005tool_call 观察 + 执行入口最终审批，失败关闭Accepted

CORE-02 实测表明：普通 tool_call 审批后仍可能有扩展改写参数。宿主必须统一包装内建工具定义、扩展注册和动态 MCP 注册，在工具 execute 入口取得最终参数的独立不可变快照，再经 IPC 等待 daemon 裁决。裁决绑定请求 ID、toolCallId、参数摘要、策略代际及有效期，只执行获批快照。观察钩子缺失、IPC 断开、超时、异常或授权失效均在真实副作用前阻断。验证实现与样本见 CORE-02；产品权限服务仍由后续阶段实现。

理由
  • SDK 的 tool_execution_start 先于 tool_call，只表示准备调用
  • 最终守卫位于所有参数改写之后，不依赖审批扩展的加载顺序
  • 审批与执行使用同一参数快照，避免等待期间被替换
  • 分类与授权留在 daemon，内核守卫负责绑定、等待、校验和执行
代价
  • 依赖扩展 API 的稳定性
  • 内核侧多一次 IPC 往返的延迟
  • 超时策略影响自动化体验
备选与否决
  • 执行后撤销：文件已落盘，无法保证一致性
  • 仅前置审批钩子：后续参数改写可绕开已批准范围
  • 仅包装初始工具列表：遗漏动态 MCP 与嵌套工具注册
  • 任意扩展直接调用文件 / 进程 API：需要 M5 系统隔离，工具守卫不构成 OS 沙箱
ADR-006以 shadow git 作为变更账本Accepted

每个工作区一个独立 git-dir（~/.pi-workbench/ledger/<workspaceHash>.git），work-tree 指向用户工作区。每轮开始打基线提交，轮次结束打快照提交；diff、逐块回滚、整轮回滚都基于提交对象。

理由
  • 独立 index 与对象库保留用户仓库原样，无需用户先 git init
  • 原始 blob 支持字节校验和文件恢复；工具前后观察链辅助归属判断
  • 逐块回滚留待 M6 单独验证；CORE-03 仅验证文件与整轮恢复
代价
  • 大仓库首次快照成本高
  • 需要维护忽略规则与二进制策略
  • Windows 路径与大小写需额外测试
备选与否决
  • 自存 diff 文本：无法检测外部修改，回滚易覆盖用户工作
  • 直接操作用户仓库的 stash/commit：侵入性强，易与用户操作冲突
ADR-007前端：纯事件 reducer + 分层状态Accepted

协议事件先经 @piw/shared 的纯函数 reducer 生成领域状态，再由 Zustand 按会话切片存放；REST 快照经 TanStack Query 缓存并与 reducer 结果合并。组件只读状态，不发请求。

理由
  • reducer 可在 Node 中单测与回放
  • 流式 token 更新只触碰当前会话切片
  • 快照与增量合并逻辑集中一处
代价
  • 需要严格的事件 schema 与版本号
  • 调试时需同时看 WS 与 Query 两层
备选与否决
  • 组件内直接 setState：流式更新引发大面积重渲染
  • Redux Toolkit：模板代码多，且与 TanStack Query 职责重叠
ADR-008本机回环 + 一次性配对 + Cookie 会话Accepted

daemon 仅监听 127.0.0.1；首次访问用一次性令牌换取 HttpOnly; SameSite=Strict 的会话 Cookie；所有写请求校验 Origin 与自定义头；WS 握手复用同一 Cookie。

理由
  • 浏览器形态无法安全保存长期 bearer token
  • SameSite + Origin 校验可挡住本机其他站点的 CSRF
  • Cookie 不进入 JS，降低 XSS 后果
代价
  • 需处理令牌文件权限与轮换
  • 多浏览器需各自配对
备选与否决
  • URL 里带长期 token：会进历史记录与日志
  • 关闭认证只靠回环：本机恶意页面可直连
ADR-009daemon 以独立 Node sidecar 交付Accepted

桌面安装包内置独立 Node 24 LTS（开发仅显式复用同一版本），daemon 作为普通 Node 进程启动，不使用 ELECTRON_RUN_AS_NODE。

理由
  • 原生模块（PTY、SQLite）只按 Node ABI 编译一次
  • piw serve 可脱离 Electron 独立运行
  • daemon 崩溃可用独立进程管理器重启
代价
  • 安装包增大（约数十 MB）
  • 需跟随 Node LTS 升级
备选与否决
  • Electron utilityProcess：原生模块需 Electron ABI，Web 形态还得再编一份
  • 纯系统 Node：用户未安装时无法启动
ADR-010pi 进程池：每活跃会话一进程，LRU 上限 3Accepted

pi SDK 子进程一次只持有一个会话。daemon 为“正在运行或待审批”的会话保活子进程；切走且空闲超过 10 分钟的子进程被回收，下次输入时按 sessionFile 冷启动恢复。

理由
  • 后台会话可继续运行，符合 PRD 的多会话并行
  • LRU 限制内存与模型连接数
  • 空闲回收避免常驻数十个进程
代价
  • 冷启动有 1–3 秒延迟
  • 切回后需重新订阅事件并校准状态
  • 会话级授权需在 daemon 侧持久化，不能只存于进程内存
备选与否决
  • 全局单进程 + 频繁切换会话：并行会话会被打断
  • 每会话常驻进程：进程与内存随会话数线性增长
ADR-005 的实现前提 每个子进程必须建立观察钩子和独立执行守卫。hasExtensionHandlers('tool_call') 只能说明存在某个处理器，不能证明宿主审批完整。启动、重载和能力变化后需验证所有可执行工具定义受包装、IPC 往返可完成、拒绝时真实副作用未发生；守卫自身在每次执行时再检查观察记录与授权。任一项失败则禁用未验证工具；未知能力不能自行归为只读。
2026-11-01 实施路线已定用户已确认 React / Vite + NestJS / Fastify daemon + Drizzle / SQLite + pi 1.4.0，pnpm 单仓库；不直接 fork PI-Desktop，不引入 Rust 宿主。完整选型、采纳矩阵、UI 时点和 M1 工作包见 实施方案。目录及模块边界见 项目结构设计；选型与安装 / 兼容验收分开。

IPC 消息要点

  • 四类帧：ready（握手）、command（下行）、response（回填 id）、event（上行）。全部是结构化对象，不使用文本行协议；因此不需要行切分，也不存在 U+2028 / U+2029 破坏帧的问题。
  • stdout 只做诊断：SDK 或依赖打印到 stdout/stderr 的内容进入环形缓冲（最多 200 行），供“查看内核日志”使用；任何日志都不进入协议通道。
  • 消息原子：单帧要么完整到达要么不到达，不存在“半行”。子进程在流式过程中崩溃时，daemon 把最后一条 assistant 消息标记为 interrupted，随后用 SessionManager 重新加载会话，而不是拼接半截帧。
  • 命令关联：每条命令生成递增 id，在 pendingCommands 中登记；响应必须带同一 id；普通 RPC 默认超时 30 秒；prompt 和本地审批等待不设该超时，可被 abort / 运行时失效取消并唤醒。
  • 事件顺序：同一子进程的 IPC 通道 FIFO；daemon 只做入队，持久化与广播串行执行，绝不在处理函数里并发 await 后乱序提交。
  • 背压：子进程对 text_delta 做 16ms 合批后再上行；daemon 单会话事件缓冲上限 2000 条，超出时丢弃最旧的增量事件但保留状态边界事件（agent_settled、tool_execution_end、compaction_end），并下发 resync_required 让客户端重拉快照。

消息与工具关联

实际 SDK 顺序是 tool_execution_start → tool_call → execute。准备事件先建立工具卡，观察钩子记录调用身份；所有扩展参数改写完成后，执行入口守卫冻结最终快照并发 approval.requested。审批卡与守卫确认后的 tool.started 按同一 toolCallId 合并。嵌套调用保留 parentToolCallId 且逐层独立裁决，父调用获批不能放行子调用。

assistant 消息内的 toolcall 参数块由 contentIndex 定位，避免在文本流中做字符串匹配。参数字符串只在 message_end 或工具执行开始时解析一次，失败则降级为原文展示。

会话生命周期与恢复

  • 冷启动：daemon 读取 SQLite 索引取得 sessionFile，fork 子进程，子进程用 SessionManager.open(sessionFile) 加载并以 createAgentSession() 重建运行时；ready 帧到达前 UI 显示“恢复中”，随后下发一次 session.state 快照完成校准。
  • 分叉：以目标 entry 的 id 调用 createBranchedSession(leafId) 或 SessionManager.forkFrom(...) 生成新 sessionFile，再为新会话 fork 子进程；变更集不继承（PRD 规定）。
  • 归档：仅标记 SQLite 索引并回收子进程；会话 JSONL 保留，可随时恢复。
  • 切换：同一时间只有一个会话在“前端聚焦”，但后台会话的子进程照常运行；所有事件按 sessionId 分流到各自的环形缓冲。
  • 回收：空闲 > 10 分钟的进程被优雅终止；终止前若处于 blocked（待审批）则不回收。下次输入时按 sessionFile 冷启动。
  • 崩溃：子进程退出时，未完成的消息标记 interrupted，未决审批标记 expired；daemon 按同一 sessionFile 重试一次，连续失败则把会话置于只读并提示诊断。

写入策略

  • 数据库文件权限 0600（Windows 用 ACL 等价设置）

消息历史与树

已提交的消息正文由 pi 会话 JSONL 保存。M2 的首次发送需要持久化创建请求与待送达首条消息，待内核 ready 后按稳定 ID 写入会话；确认送达后清理待送达副本，重试先核对接收状态，结果不确定时不自动重放。子进程启动或恢复时用 SessionManager 加载会话文件，按 id / parentId 重建树；前端默认展示当前分支的线性视图，分叉入口来自 getUserMessagesForForking() 与 getTree()。当 JSONL 某行损坏时保留原始记录、标记 partial_history 并暂停继续执行，提供导出与恢复入口，不静默截断后继续写入。

不要镜像消息 把 assistant 消息全量写入 SQLite 会带来三个后果：与 pi 的双写不一致、上下文压缩后历史失真、升级时字段漂移。工作台只存“展示所需的派生摘要”（标题、最后更新时间、轮次数），正文永远回源。派生搜索索引可重建，不能用片段或展示截断内容回写历史。独立 inflight 文件以消息 / 轮次 / 运行时代际记录流式检查点，目标间隔 1.5 秒；恢复仅展示中断内容，不伪造 SDK 历史、不自动重放工具。

变更账本（shadow git）

变更不是“把 diff 存起来”，而是“能在任意时刻知道文件在轮次前后的确切内容，并在冲突时拒绝覆盖”。shadow git 用独立对象库记录这些事实，用户仓库完全不受影响。

目录与初始化

~/.pi-workbench/
├─ ledger/
│  └─ <workspaceHash>.git/      # 独立 git-dir，永不写入用户 .git
│     ├─ objects/              # 快照对象（按内容寻址）
│     ├─ refs/piw/turns/<sid>/ # 每会话轮次引用，便于 GC
│     └─ info/exclude          # 镜像用户 .gitignore + 内置排除
└─ workspaces.json             # 路径 → 账本目录映射

# 所有命令统一形式（不切换当前目录、不读取用户 git 配置）
git --git-dir=<ledger> --work-tree=<workspace> -c core.excludesFile=<exclude> …
# 环境隔离：GIT_CONFIG_NOSYSTEM=1、GIT_AUTHOR_NAME=pi-workbench、GIT_TERMINAL_PROMPT=0

轮次算法

  1. 轮前：按物理目录唯一映射取得受管写入锁，重新读取普通文件（包含用户 staged / unstaged / 未跟踪内容），双扫描检测期间变化。使用独立 index、原始字节 hash-object --no-filters 与 commit-tree 生成 P。成功持久化基线前不执行受保护写入；不写用户 index 或 HEAD。
  2. 轮中：在最终执行入口对文件工具记录目标、toolCallId、执行前后哈希与预期结果，校验连续工具链。工具前状态不匹配、工具失败或输出不匹配均标为来源混合。命令中无法确认的文件变化标记未知。
  3. 轮后（agent_settled）：重新扫描，记录 H 与运行结果（成功 / 错误 / 中止分开）；对每个差异计算支持范围及 agent-observed / mixed / unknown。未记录工具链不能仅凭 P..H 推断作者。末态失败标记快照缺失，禁用可靠回滚。
  4. 变更集：生产阶段写入 SQLite（changeset + file_change）；P 为恢复目标、H 为当前适用性校验依据。CORE-03 候选以独立 JSON / Git 对象持久化，未实现产品 SQLite 或 UI。
  5. 空轮次：P 与 H 相同则不产生变更集，只保留审计记录。

回滚

操作实现前置校验
回滚代码块M6 独立实现和验收，基于已校验版本构造逆向补丁支持范围、上下文适用性与外部编辑须单独检查
回滚文件验证 manifest / 原始 blob 完整性后直接写回 P 字节，不操作用户 index；新增删除、删除恢复，重命名按增删成对恢复前后均支持、来源可确认、当前内容等于 H；保留原有脏内容
回滚整轮共用工作区锁；先读出并校验所有对象及当前末态，开始应用前再次全量检查，逐文件写入前复检并记录 journal任一预检冲突整批不写；运行期失败逆序有条件补偿，无法补偿则标记 needs-recovery，保留现场
接受只改 file_change.status，不触碰文件接受不等于提交，PRD 已明确
冲突定义 当前文件与记录末态字节不一致时阻止回滚；来源混合、快照缺失或对象损坏也会独立禁用回滚。用户可手动对比、选择可确认的文件；后续显式覆盖需单次授权和审计。双扫描及路径复检无法彻底消除 OS 写入竞态，多文件写回不是系统事务；补偿时遇到新的外部编辑必须保留并提示恢复，不能宣称全批天然原子。

排除、二进制与大文件

  • 排除规则：遵守工作区 .gitignore，内建排除 node_modules、.git、.pi-workbench 及嵌套仓库。明确列出不完整范围；忽略文件只保存大小 / mtime，排除目录不扫描内部内容，不承诺完整列出其变化。受保护工具写入默认拒绝。
  • 二进制：--numstat 输出 - 即判定为二进制；变更集只展示文件名、大小与“不可逐块审查”，回滚按整文件。
  • 大文件阈值：CORE-03 候选单文件 > 5 MiB 分块哈希，仅记录哈希与大小，不存 blob、不可自动回滚；200 文件延迟 hunk 与大仓库性能仍待 M3 验证。
  • 链接 / 子模块：CORE-03 保守排除 symlink / junction / hardlink 和嵌套仓库，拒绝跟随，外部 sentinel 保持原样。本机文件 symlink 创建返回 EPERM，未将未运行的执行验证算通过；实际 junction / hardlink 测试通过。权限 / ACL、空目录、仅大小写重命名、其他平台留待生产验收。
  • 并发写入：同物理目录的受管写入及回滚共用唯一账本锁，真实并行使用 Worktree。外部编辑不受锁控制，归属依工具链和内容校验保守判断；mtime 仅作提示，不能证明作者。同字节覆盖及短暂外部改动无法完全检测。

审批与风险引擎

审批的目标不是“多弹窗”，而是让每一次有副作用的动作都有明确的授权来源。风险引擎只做分类，执行守卫负责最终绑定与阻断，daemon 做唯一裁决，三者职责不重叠。

风险分级

等级判定对象默认动作可否会话级授权
L0只读：列出目录、读取工作区内文件、查询 git 状态自动放行，仅记录不适用
L1工作区内写入、创建、删除单文件需审批可按路径前缀授权（如 src/auth/）
L2命令执行、网络访问、读取工作区外路径需审批可按命令前缀授权（如 npm test --）
L3工作区外写入/删除、系统级操作、凭证访问、不可逆动作需审批，且每次都要确认禁止会话级授权

分类算法

收集所有匹配规则并取最高风险；以下规则的书写顺序不代表优先级，不得首次命中即停止。扩展改写参数后重新对最终参数裁决，未分类默认 L2：

# 规则文件：~/.pi-workbench/policy.yaml（只读，UI 不直接编辑）
rules:
  - id: read-only
    match: { tool: [read, list, grep, glob], path: inside }
    risk: L0
  - id: write-inside
    match: { tool: [edit, write], path: inside }
    risk: L1
  - id: shell
    match: { tool: bash }
    risk: L2
  - id: outside
    match: { path: outside }
    risk: L3
  - id: destructive
    match: { command: 'rm -rf|mkfs|format|shutdown|reg delete' }
    risk: L3
  - id: credentials
    match: { path: '~/.ssh|~/.aws|**/.env*' }
    risk: L3
default: L2
  • 路径判定：先 realpath 解析，再做前缀比较；符号链接指向工作区外按“工作区外”处理。
  • 命令判定：做有限解析（可执行名 + 前两个参数），不追求完整 shell 语义；含管道、重定向、&& 时整条按 L2 以上处理，且不允许会话级授权。
  • 工具来源：内建工具、MCP 工具、扩展工具统一进入分类；未知工具名默认 L2。
  • 参数被改写：扩展若 mutate 参数（例如把相对路径改成绝对路径），必须重新分类一次，避免“先按 L1 批准、后按 L3 执行”。

授权（Grant）

维度规则
作用域仅限当前会话；会话归档、结束或内核重启后全部失效（持久化审计仍保留，服务或内核重启后不恢复旧授权）
匹配命令按前缀字符串匹配 + 参数边界；路径按规范化前缀；不做通配符扩展
收紧设置中提高审批等级时，立即吊销所有低于新等级的 Grant
撤销P0 仅提供“撤销全部授权”；单条撤销 [TBD]
L3永不产生 Grant，每次弹窗都必须人工确认

审批钩子契约

环节内容备注

Electron 外壳

主进程只做“系统的事”：单实例、窗口、daemon 监护、更新、深链。渲染进程加载的是 daemon 提供的页面，因此桌面与浏览器在协议、Cookie 与安全模型上完全一致。

进程模型

进程职责安全设置
main应用生命周期、单实例锁、窗口状态、daemon 启停与健康检查、更新、深链、菜单与托盘不加载远程内容；所有 IPC 处理器做参数校验

daemon 监护

  1. 启动时读取 ~/.pi-workbench/daemon.json；若 pid 存活且 /api/health 可用，直接复用（支持“先开 Web 再开桌面”）。
  2. 否则 spawn sidecar：<resources>/node/node[.exe] <resources>/daemon/index.mjs --port 0，环境注入数据目录与日志目录。
  3. 轮询健康检查，最多 15 秒；失败展示可复制的诊断（stderr 尾部 + 路径 + 版本）。
  4. 运行期每 10 秒心跳；连续 3 次失败则重启，最多 3 次，之后进入“服务不可用”状态，UI 可手动重试。
  5. 退出时先发 SIGTERM，等待 5 秒；超时 SIGKILL。异常退出留下 crash-<ts>.log，下次启动提示查看。

  • 文件打开事件：在工作区内的文件可定位到变更集

Web 外壳与认证

网页端不是“把桌面版放到服务器”，而是“浏览器访问本机同一实例”。因此认证目标只有一个：证明请求来自用户本人，而不是本机另一个网页或局域网中的设备。

会话与注销

  • Cookie 有效期 7 天 [TBD]，滑动续期；daemon 重启后失效，需重新配对（安全优先）。
  • piw pair --revoke 清空所有会话并轮换令牌；桌面端“退出网页登录”执行同一动作。
  • 多浏览器各自配对，互不影响；同时打开的多个标签共享 Cookie，但独立 WS，裁决冲突由服务端条件更新兜底。
  • 远程终端开关默认关闭，且只能在本机桌面或 CLI 显式开启；网页端只读展示开关状态，不能打开。
不要为 Web 增加“远程访问” P0 明确不支持跨机器访问。若未来需要，必须新增独立 ADR，引入 TLS、设备配对、权限分级与审计，不能仅把监听地址改成 0.0.0.0。

终端与任务执行

终端是“用户亲手输入的命令”，任务面板是“用户显式提交的批处理”。两者都不经过 agent 审批链，但与 agent 工具执行严格区分，避免授权语义混淆。

终端

环节实现约束

ShellWindows 优先 pwsh → powershell；Unix 用 $SHELL → /bin/zsh → /bin/bash启动前检测可执行文件存在，失败给明确提示

流控服务端按 16 ms 合并输出；客户端每 200 ms 回执已消费字节数未回执超过 512 KB 时暂停读取，防止内存膨胀

审计与隐私：终端开启、关闭、远程开关切换写审计；默认不记录命令内容与输出（避免把密钥写进日志）。若后续需要“命令历史”，必须单独开关并明确告知 [TBD]。

为什么终端不走审批 终端命令由用户在可见的终端里亲手输入，用户本人就是授权来源；若再套一层审批，会变成“确认自己的输入”。agent 发起的 bash 工具则必须审批，因为它的意图与参数由模型生成。两类执行在 UI 上必须视觉可区分：终端标签带“手动”标识，工具卡带风险等级。

任务

任务面板用于“跑一次命令、拿退出码与日志”。执行由 daemon 直接管理，不依赖某个会话是否存活：命令在独立子进程中运行，输出写入 ~/.pi-workbench/tasks/<id>.log，库内只保存摘要与指针。

阶段行为
提交校验 cwd 在工作区内；命令非空；长度上限 4096；运行前做 L3 模式预检（rm -rf、format、shutdown 等）并要求二次确认
排队同时运行上限 3；超出进入队列，UI 显示“排队中”
运行spawn(shell, ['-lc', cmd])；stdout/stderr 合并为带通道标记的行；每 100 ms 批量推送 task.output
结束记录退出码、耗时、输出字节数；非 0 标为失败；输出超 2 MB 截断并保留头部与尾部各 1 MB
停止SIGTERM → 5 秒 → SIGKILL；标记 stopped，不伪造退出码
注入仅在用户确认后，把“命令 + 退出码 + 日志摘要（默认末 40 行）”作为用户消息写入当前会话

与 agent 的边界

维度agent 工具 bash终端任务
发起者模型用户用户
审批必须（L2+）无（输入即授权）L3 模式二次确认

生命周期随子进程随 daemon独立，可跨会话

进程清理 所有 PTY 与任务必须在 daemon 收到 SIGTERM 时进入“终止中”状态：先停止接受新任务，再 SIGTERM，最后统一 SIGKILL。异常崩溃后由下次启动的 piw doctor 扫描遗留 pid 并清理，避免孤儿进程占端口或锁文件。

安全与隐私

威胁模型的核心不是“防黑客”，而是“防止 agent 或页面在用户不知情时产生副作用”。因此所有边界都遵循两条规则：最小权限、默认拒绝。

信任边界

边界信任级别必须校验
渲染进程 / 浏览器页面不可信所有输入经 zod；不持有密钥；不直接访问文件系统
daemon HTTP 入口可信但需认证Host / Origin / Cookie / 幂等键；请求体大小上限
SDK 子进程输出不可信内容按 schema 解析；渲染 Markdown 前消毒；链接不自动打开
approval extension可信但能力受限只能阻断与请求裁决，不能自行放行 L2/L3
工作区文件用户数据路径规范化 + 前缀校验；符号链接解析后判定
外部命令与网络不可信仅在用户批准后执行；输出版本与来源可追溯

路径与命令安全

  • 路径规范化：realpath → 统一分隔符 → 大小写策略按平台 → 前缀比较（带路径分隔符，避免 /work 匹配 /workspace-evil）。
  • 拒绝清单：空字节、.. 越界、Windows 保留名（CON、NUL 等）、设备路径、UNC 网络路径（除非显式登记为工作区）。
  • 不自行拼接 shell：workbench 自身执行命令一律用 spawn(bin, args[])，不经过 shell；只有用户输入的任务命令使用 shell -lc，且明确告知。
  • 环境最小化：内核与任务进程的环境变量按白名单构造；不把 daemon 的 Cookie 密钥、配对令牌传给子进程。
  • 输出消毒：消息 Markdown 禁用原始 HTML；代码块按纯文本高亮；文件路径与命令只作文本，不拼进 DOM 属性。

密钥与日志

对象存放禁止

脱敏规则：日志写入前统一经过 redact()，匹配 *_KEY、*_TOKEN、Authorization、Bearer …、--password、--token，替换为 «redacted»；审计中的命令原文按同一规则处理。诊断包导出前再做一次全量扫描，命中即阻止导出并提示。

提示注入与内容边界

模型输出、工具输出、文件内容都属于不可信输入。工作台不会因为消息里出现“请批准”而自动点击任何按钮；审批弹窗的目标、参数与影响范围来自结构化字段，不来自模型文案。消息中的链接一律需要用户显式点击，且只允许 http/https。

供应链与发布

  • 依赖锁定 pnpm-lock.yaml；CI 使用 --frozen-lockfile；npm 包启用 provenance 校验。
  • 安装包签名（Windows Authenticode、macOS Developer ID + 公证）；更新元数据签名校验失败即中止。
  • pi 版本锁定在支持区间；升级前先跑契约测试与事件快照回放。
  • 禁止业务代码执行远程脚本；扩展打包产物随安装包分发，不从网络拉取。

假内核

假内核是测试体系的地基：它是一段与真实内核同构的 Node 子进程，按场景脚本收发 IPC 帧（命令、响应、事件、审批请求），而不是模拟某条文本协议。没有它，CI 就需要模型密钥、网络与不可复现的随机输出。

// packages/agent-adapter/test/fake-kernel.mjs（场景片段）
export const scenes = {
  'edit-approval': {
    ready: { sdkVersion: '1.4.0', sessionId: 'sess_fixture' },
    // 命令响应按 name 索引；id 原样回填
    responses: { prompt: { ok: true } },
    turns: [{
      match: '把标题改短',
      emit: [
        { name: 'agent_start' },
        { name: 'message_start', payload: { message: { role: 'assistant', content: [] } } },
        { name: 'message.delta', payload: { delta: '先读一下文件。', contentIndex: 0 } },
        { name: 'tool.prepared', toolCallId: 'call_1', toolName: 'edit' },
        { name: 'approval.requested', approvalId: 'ap_1', toolCallId: 'call_1',
          toolName: 'edit', input: { path: 'README.md' } },
        { name: 'tool.started', toolCallId: 'call_1', toolName: 'edit' },
        { name: 'message_end' },
        { name: 'agent_settled' }
      ]
    }]
  }
}
  • 三种模式：scripted（按脚本）、echo（把 prompt 逐字回显为增量事件，用于压测）、fault（注入崩溃、卡死、重复 id、非法帧、超大消息）。
  • 确定性：时间戳、会话 id、工具 id 由固定种子生成；同一场景重复运行字节级一致。
  • 保真约束：假子进程收发的帧先经过真实 zod schema 校验；字段名或结构写错会直接让测试失败，而不是让前端“看起来能用”。

事件快照回放与录制

真实 SDK 子进程的 IPC 帧是唯一事实。录制时以 PIW_RECORD=1 运行一次真实对话，把适配层收发的帧原样落盘为 fixtures/sdk-1.4.0/<scene>.jsonl；回放时逐帧喂给 adapter 与 reducer，断言最终快照与关键中间状态。录制内容按脱敏规则剔除模型凭据与敏感参数。

用例覆盖断言重点
G1纯文本对话增量拼接无重复、无丢失；agent_settled 后状态回 idle
G2工具调用 + 审批SDK 准备事件先到；最终快照获批后才有宿主 tool.started；调用 ID 关联一致，拒绝后真实副作用未发生
G3编辑审批与拒绝拒绝后钩子返回 block，工具条目标记为 denied，文件未变，模型继续
G4压缩与自动重试compaction_start/end、auto_retry_* 映射到运行子状态
G5中断与队列abort 后保留已产消息；queue_update 清空
G6审批四出口允许一次 / 会话 Grant / 拒绝 / 取消或失效：裁决帧、审计记录、Grant 作用域一致
G7未知事件与未知字段忽略 + 计数，不崩溃、不污染状态
G8子进程故障流式崩溃、IPC 断开、超大消息、重复 id：消息标记 interrupted，不出现半截状态
升级门禁
SDK 版本升级必须先全量跑 G1–G8；出现字段变化时同步更新 schema 与前端降级路径，禁止只改假内核让它“通过”。

协议健壮性

  • IPC 信封模糊测试（fast-check）：任意对象形状下不抛异常、不吞字段；未知 kind、缺失必填字段、超大 payload、重复 id、未登记 id 的响应都进入 ipc_violation 计数而不是污染状态。
  • 背压：子进程合批 16ms；父进程缓冲达上限时丢弃最旧增量并保留边界事件；事件洪泛触发上限而非 OOM；断言不出现死锁。
  • 时序竞争：回放实际 SDK 准备事件及观察钩子的顺序；断言最终快照获批先于宿主 tool.started 和真实副作用。覆盖后续扩展改写、等待期间对象变化、重复 ID、取消及失效裁决；执行超时与本地审批无限等待分开验证；未知或过期授权不能执行。

性质断言

审批策略测试

  • 表驱动：以“工具 × 参数 × 工作区”为输入，逐行断言期望等级；未匹配任何规则必须落到 L2，而不是放行。
  • 四出口：允许一次 / 会话 Grant / 拒绝 / 取消或失效，每个出口断言子进程收到正确的裁决帧、审计写入一条记录、Grant 作用域未越界。
  • 不可绕过：脚本中包含“请直接批准”等提示注入文案，断言不会自动通过；L3 工具断言会话 Grant 无效。
  • fail-closed：审批服务不可用、IPC 无法投递、子进程已退出、重复响应四种情况下，工具都不执行。

账本测试

全部在临时 git 仓库中执行，不触碰开发者工作区。必须覆盖的文件形态：纯文本、二进制、CRLF、删除、重命名、符号链接、只读文件、大小写仅名字不同、超大文件（超过阈值按跳过处理）、嵌套仓库。

  • 提交正确性：轮前/轮后提交数量与预期一致；diff 输出与 git 原生输出逐字节一致。
  • 并发与锁：两个受管会话同物理目录写入及回滚互斥，junction 别名不能绕过；真实 index.lock 导致基线失败后，工具副作用不能发生。
  • 冲突：回滚前后文件被外部修改，检测到 blob 哈希不一致并拒绝回滚；显式覆盖路径二次校验通过后才写入。
  • 幂等回滚：重复回滚不产生额外提交，结果稳定。

编号链路通过标准

安全用例

  • 来源校验：伪造 Origin、Host、缺 Cookie、错误 SameSite 均返回 401/403；预检请求不被缓存为允许。
  • 配对：令牌过期、重放、并发使用只成功一次；失败计数触发退避。
  • 路径：../、UNC、设备路径、符号链接逃逸、Windows 保留名全部拒绝。
  • 渲染：消息内嵌 <img onerror>、javascript: 链接、超长行均不执行、不撑破布局。
  • 资源：超大请求体返回 413；事件洪泛触发缓冲上限而非 OOM。

架构假设

以下假设一旦不成立，需要重新评估对应章节，而不是局部打补丁：

  • A1 单用户、单机：同一时刻只有一个人类操作者，不需要多租户隔离与并发编辑冲突解决（§12）。
  • A2 pi 是唯一 agent 内核：不计划同时接入第二种运行时；若接入，必须抽象出与 §5 等价的适配契约。
  • A3 扩展钩子能覆盖全部会产生副作用的工具：这是审批体系的成立前提（R2）。
  • A4 工作区是本地目录且用户对其有写权限；远程工作区、容器内工作区不在 P0 范围。
  • A5 git 可用：账本依赖本机 git 可执行文件，缺失时降级为“无变更集”模式并明确提示。
停止条件
若 R1 与 R2 同时成立（协议频繁变化且钩子覆盖不全），当前“包装内核 + 审批桥”的方案不再成立。此时的替代方案是：放弃实时包装，改为只读会话浏览 + 人工复制提示词，直到上游提供稳定的拦截接口。

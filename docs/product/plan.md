# Pi Workbench 全量产品规划

版本：1.9 · 基线日期：2026-11-02 · 状态：范围与实施路线已定，按阶段细化与实现

## 产品目标与可行性

以 pi agent 为执行内核，建设一个面向个人开发者、本地优先的完整编码工作台。目标体验覆盖项目与会话、任务输入、过程观察、权限控制、代码审查、文件与网页预览、Git / Worktree、扩展、多 Agent 与自动化。

这一目标在结构上可行。本机已安装 `@earendil-works/pi-coding-agent@1.4.0`，其 SDK 文档与类型声明提供会话、流式订阅、steer / followUp、abort、压缩、分叉、模型配置和扩展事件。MCP 在 SDK 模式需要显式加载相应扩展。工具执行前的 `tool_call`、嵌套调用和多个扩展的最终参数约束，必须在 M0 用真实运行验证。

工作台负责补齐持久化索引、服务协议、权限策略、文件快照、UI、终端、Git、PR、通知、调度与分发。沙箱、跨主机执行、浏览器和计算机操作需要额外适配或服务。模型的推理质量、上下文能力、订阅权益和专有云服务不能由外壳等价复制。

“功能接近 Codex”是能力和工作流的参照，不代表逐版本完全复制。官方公开文档仅用于核对能力范围；本产品的真实状态由独立验收决定。

## 范围分层

完整本地产品包括 M0–M7。先把全量范围列清楚，再逐阶段把条目拆成可实现的工作包。后续阶段的存在不阻止前一阶段交付。

| 层级 | 交付阶段 | 能力结果 |
| --- | --- | --- |
| 技术前提 | M0 | 核实真实 SDK、执行前拦截和文件快照的成立条件 |
| 运行底座 | M1 | 可恢复的内核、事件协议、持久化与资源管理 |
| 受控试用 | M2 | 双端对话、工具观察与审批，以及项目 / 无项目会话、自动命名与搜索 |
| 首个完整闭环 | M3 | 修改归属、Diff 审查、文件回滚和冲突恢复 |
| 日常开发 | M4 | 文件上下文、终端、后台任务、配置、用量与压缩 |
| 稳定桌面版 | M5 | Windows 分发、真实权限边界、备份、升级和可靠性 |
| 完整编码工作台 | M6 | Worktree、Git、PR、代码审查、扩展管理与产物预览 |
| 高级本地能力 | M7 | 子 Agent、计划、预算、周期运行与持续跟进 |
| 可选产品线 | M8 | 局域网、SSH、云端、团队、移动端、浏览器、语音及更多产物 |

M8 不计入本地完整版完成率。它是候选需求池，每项在实现前单独确认用途、成本、数据和权限边界。无需为了实现本地工作台而建设云端账号、计费和团队 SaaS。

原有“本次不做”调整为阶段边界：自动提交 / 合并 / 部署不属于默认行为；用户明确发起的 Git 提交、推送和 PR 操作纳入 M6。多 Agent 与自动化纳入 M7，局域网及跨主机能力移至 M8。

## 关键产品决定

完整决定以 backlog 的 D01–D15 为准，并在看板“产品决定”页展示。以下规则在开始编码前优先统一：

1. 同一物理目录只允许一个 agent 写入轮次；并行写入使用独立 Worktree。终端和外部编辑的混合变更不自动归为 agent 独占修改。
2. 产品轮次与底层模型回合分开。引导进入当前轮；追加在宿主完成 settled 与快照后开启下一轮。两类队列各自保序。
3. 风险规则取所有命中的最高级，审批绑定最终执行参数。扩展改写和嵌套调用不能扩大已经批准的范围。
4. 会话授权可查看和撤销。收紧审批表示要求更多确认；关闭“要求审批”属于放宽。L3 始终单次确认。
5. 写入前基线失败时暂停，明确用户单次接受不可回滚风险后才继续。忽略项、大文件、外部路径和命令副作用有独立可回滚说明。
6. 分别显示运行结果、审查进度和文件当前适用性。全部文件分别接受或回滚后，审查进度可以达到全部已处理。
7. 分叉默认只复制历史，不恢复历史文件、不复制授权。需要历史文件时单独选择快照或 Worktree。
8. 浏览器关闭只断开查看；桌面 × 默认收到托盘继续已有任务；菜单退出应用停止其受管服务、Agent、命令与终端；独立 serve 显式退出。开机自启默认关闭。重启只恢复记录，不恢复旧授权或自动重放副作用。
9. M0–M7 默认回环访问。局域网与跨主机执行留在 M8，不混入本地浏览器配对的默认权限。
10. 新会话页先保留草稿，首次发送才创建持久会话；项目可选。默认本地摘要命名，模型润色默认关闭，不阻塞响应、不覆盖人工改名。项目归属与实际执行目录分开，整理会话不隐式切换目录或权限；无项目会话使用宿主管理的独立目录。

新会话默认仅自动执行经验证的受限读取；写文件和命令先审批，可显式授予有范围的会话权限，高危操作始终单次确认。不能把任意 Shell 命令标注为只读后放行。本地交互审批无倒计时，离开或短暂断线时保持等待；明确取消、参数 / 策略失效或服务 / 内核退出时终止旧请求，不自动执行。初始资源上限为 3 个活跃内核、1 个模型任务、6 个终端；超限排队，待审批不回收。资源上限是待实测的初始配置；无人值守策略独立验收。

M2 补齐基础项目管理、无项目会话、自动命名、重命名及标题 / 正文搜索。具体流程、失败恢复和迁移规则见会话与项目详细设计；M6 仍负责工具日志和文件引用的高级检索。

每条功能拥有固定 ID、模块、阶段、优先级、设计状态、实现来源、依赖、验收项、负责人、目标日期、阻塞说明和验证证据。后续可增补条目，既有 ID 不重用。未估算工时的条目不提供虚构日期。

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| 未开始 | 尚无可验证的实现工作 | 默认基线 |
| 进行中 | 正在设计细化或实现该功能 | 填写实际进展；功能已有范围与验收边界 |
| 受阻 | 有不能独立消除的阻塞 | 必须记录阻塞原因和需要的处理 |
| 待验收 | 实现候选已完成，仍需验证 | 提供代码位置或候选产物，不能提前计入完成 |
| 已验收 | 该条目的验收要求已经满足 | 依赖已验收、验收项全部通过且有非空验证证据 |
| 暂缓 | 明确暂不交付 | 保留理由，不算已完成 |

设计状态单独记录为“已列范围，待细化”或“已有详细设计，待校正”。已有原型、架构描述或本机 SDK 安装不等于本产品已验收。

完成率采用条目计数：已验收功能数 / 范围内功能总数。默认完整本地产品分母为 M0–M7；M8 单列。条目大小不同，因此这个数不是工时完成率，也不用于预测日期。每个阶段还需通过其跨功能验收门，不能只靠条目数宣布可以发布。

## 将功能继续拆成实施任务

进入某阶段时，对其中功能补充：触发与前置条件、用户可见流程、对象与权限、异常恢复、兼容边界、数据迁移和测试样本。每项再拆成可评审工作包，至少标注：

```text
关联功能：CHANGE-05
工作包：回滚整轮的冲突预检
前置：CHANGE-01 / CHANGE-02 / CHANGE-03
产出：实现位置、界面状态、错误行为与回归用例
验收：任一文件冲突时整个批次不写入；已有脏改动保持完整
证据：提交 / 文件位置 + 实际验证命令及输出或演示记录
```

本阶段详细设计应回填已有 PRD 与架构中的相关条目。旧的 11 项功能编号继续作为交互章节引用；新功能使用 backlog ID 管理，不能再把一组几十个子功能统称为“一个 P0”。

交互式 PRD v2 将 M0–M8 的范围映射到界面和旅程，参考 Codex 的项目 / 会话与审查工作流，以及 Claude Code 的任务模式、上下文入口、按需面板和后台任务。它补齐设计评审入口，不替代各阶段的真实实现与验证。构建方式为 `node scripts/planning/build-prd.mjs`；需求基线更新后与看板一同重建。

## 如何维护

直接编辑 `docs/product/backlog.json`，随后运行：

```powershell
pnpm docs:build
pnpm docs:check
```

生成器检查 ID、依赖、循环、跨阶段依赖和完成证据，并生成 HTML 看板、Markdown 清单与同源 PRD。检查命令同时验证本地链接和目录约定。看板支持本浏览器保存进度、导入和导出；浏览器存储只是工作副本，不会自行改写源文件。

重新生成后若项目基线版本变化，看板不会自动套用旧浏览器副本，避免旧进度遮蔽源文件中的新记录。页面会提供旧副本导出入口；对照当前基线后再显式导入需要保留的进度。显式导入当前版本数据通过校验后会重新尝试启用浏览器保存，替换前自动下载未加载的旧副本。

要把看板导出的进度回写数据源：

```powershell
node scripts/planning/build-roadmap.mjs --import "导出的 JSON 文件路径"
pnpm docs:build
pnpm docs:check
```

导入只接受既有功能的进度字段；功能定义、依赖和验收项仍由源文件维护。需要把导出文件交给后续聊天时，直接提供该文件路径即可。跨浏览器使用前先导出再导入，避免误以为进度已经跨设备同步。

## 协作方式

按主题分轮问答，每轮通常 2–3 个问题。每个问题说明推荐方案、主要取舍和影响；用户可以选推荐、修改推荐或直接描述偏好。上轮由助手确定的工程方案是本轮评审基线，用户逐项确认记录见下表。新选择确认后同步实施方案、相关 PRD 和 backlog 定义。

区分用户已经明确的要求、助手的推荐、用户本轮确认，以及仍需实际验证的工程假设。未答复不表示同意，预选推荐不表示已经提交。设计确认与功能实现分别记录，不因此勾选验收或增加完成数。

优先确认影响返工的产品形态、技术栈、代码结构和核心 UI。可用离线样本制作设计稿；正式前端实现以对应页面设计确认为前提。后续模块在进入其阶段前主动提问，不把 M6–M8 的细节当作 M1 的开始条件。

### 第 1 轮补充：运行时、框架与数据库

用户先询问 Node / NestJS / SQLite 层级，随后明确选择 NestJS + Fastify 适配器、SQLite + pi JSONL；第 2 轮又确认 React 组合、单仓库与 Drizzle + better-sqlite3。以下保留理由与真实验证边界。

| 层级 | 作用与推荐 | 取舍 / 待验证事项 |
| --- | --- | --- |
| Node | 执行服务端 TS / JS 及 pi SDK 的运行环境；24 是成熟且仍受支持的 LTS 基线 | Node 26 在当前日期也已进入 LTS，不把 24 称为最新或唯一选择。SDK、better-sqlite3、node-pty、安装包的兼容性决定最终精确版本；独立内置 Node 不要求替换用户系统 Node |
| NestJS | 应用框架：模块、依赖注入、生命周期及统一组织方式 | 项目后端有会话、项目、权限、队列、账本、终端等长期模块，结构约定有价值；增加依赖、装饰器 / DI 和启动开销，不能当作性能升级 |
| Fastify | HTTP 服务框架，可以直接使用，也可作为 NestJS 的适配器 | 推荐 NestJS + FastifyAdapter 组合；Express 专用中间件不能直接当作 Fastify 插件。REST / WS 鉴权、关闭顺序、测试与打包须在 OPS-01 验证 |
| SQLite | 嵌入式本地数据库：项目 / 会话索引、待送达请求、队列、审批、审计和派生搜索索引 | 不需要数据库常驻服务或独立账号。单库同时一个写入者，本项目由 daemon 串行短事务写入；不能把此架构直接承诺给未来多人共享服务 |
| pi JSONL / 账本 | 消息由 SDK 的原生 JSONL 保存，受保护文件快照由独立 Git 账本管理 | SQLite 不成为另一份权威消息正文或文件快照；密钥不进入普通业务库，备份应使用一致性备份方法 |

基于长期领域模块与依赖关系，NestJS + Fastify 适配器已获用户选择，正式替代直接 Fastify 的轻量组织方式。模型调用费用主要由提供商、模型、token 与工具循环决定，上述框架和本地数据库选择不会直接减少或增加模型 API 单价。

| 编号 | 本次补充提问 | 推荐 | 用户回答 | 状态 |
| --- | --- | --- | --- | --- |
| R1-02a | 后端用 NestJS + Fastify，还是直接用 Fastify？ | NestJS + Fastify 适配器 | “NestJS + Fastify 适配器（推荐）” | 用户已确认 |
| R1-02b | 本地索引用 SQLite + pi JSONL，还是现在引入 PostgreSQL 等独立数据库？ | SQLite + pi 原生 JSONL | “接受 SQLite + pi 原生 JSONL（推荐）” | 用户已确认 |

- [Node 发布周期](https://nodejs.org/en/about/previous-releases)
- [Nest 官方 Fastify 适配包元数据](https://registry.npmjs.org/@nestjs/platform-fastify/latest)

## 高保真设计应交付什么

先确认设计方向，再精修页面。方向稿用于比较主要工作区、输入、工具过程、审批和审查的关系；使用本地 HTML / CSS 或 SVG 绘制并在浏览器实际渲染，可同时提供截图与可点击稿。它们是界面设计，不使用模型伪造运行证据。

核心页面至少覆盖：

1. 新会话：项目可选、独立草稿、真实执行位置、模型 / 模式与首次发送。
2. 正在运行：流式回复、折叠工具、引导 / 追加、停止、后台状态。
3. 待审批：最终参数、影响范围、允许 / 拒绝 / 取消与授权管理。
4. 会话组织：项目、最近、置顶、搜索结果、改名和无项目归属。
5. 修改审查：文件列表、Diff、接受 / 回滚、混合来源、冲突与恢复。
6. 开发工具：文件上下文、终端 / 后台任务、与审查同屏的布局。
7. 设置与数据：提供商配置状态、权限、费用未知 / 预算、外观、数据与诊断。
8. 共通状态：空、加载、排队、离线、失败、中断、恢复、长中文 / 路径、窄窗口与放大。

M6–M8 页面保留范围；在开发对应模块前补充高保真细节，不阻塞前期核心页面。确认产物包括设计 tokens、组件状态、页面布局、交互行为和响应布局，而非只确认一张静态首页。

## SEC-07：资源信任的保留（已确认）

用户选择“保存并复用，变化后重新确认（推荐）”。资源信任按实际目录、单项来源和内容指纹保存到 daemon 的 SQLite，重启后仅复用完全匹配的版本；未匹配的内容或来源需要重新确认。用户可查看并撤销记录。此记录仅表示资源加载意愿，不授予工具、文件、命令或网络权限，不恢复执行审批。

实施细化：撤销从后续轮次生效，已开始的轮次保留不可变资源快照，停止任务仍单独操作；不回写历史或用户配置。当前仅向受管 SDK 显式传入已确认的上下文文本；原生扩展、脚本、安装动作和设置合并继续禁用，按 EXT / EXEC / SEC 对应条目另行接入和验收。这些实现约束不冒充用户已逐条选择的未来扩展方案。

## SESSION-03：未读清除时机（已确认）

2026-11-03 用户选择“读到最新才清除未读（推荐）”。新完成、失败或中断结果标为未读；打开会话本身不清除。当前窗口可见且有焦点、对话实际滚动到最新，并已展示对应结果后才提交已读回执；支持手动标记已读 / 未读。手动标未读不会因原地轮询立即清除，重新进入或继续阅读到最新后可清除。

归档沿用既有 PRD 的先停止规则：运行时说明影响，明确请求停止，等待 daemon 确认任务结束，再由用户单独确认归档。待审批 / 待处理队列须先处理；当前整理入口不代替尚未交付的生产审批流程。恢复只恢复列表，不恢复授权或启动任务。

## WS-06：项目排序与移除（已确认）

2026-11-03 用户选择“采用推荐规则”：已置顶项目在前，各组内手动上移 / 下移，新项目放在未置顶组末尾，跨重启保存。置顶 / 取消置顶放到目标组末尾；检索不改变持久顺序，上下移按完整组的相邻位置执行。后两项是该规则的实现细化。

## 收敛中的并发复核

初轮完整 CI（431 项 Vitest、162 项 E2E、SDK）通过后，独立实际服务复现了项目移除等待竞态与模型排队期间文件变化；新增两项回归在修复前失败。最终方案在引用 IO 后、原子保存前重查归属，并在内核资源准入及实际发送前沿用 preflight 重验版本。失效记录保存具体原因，禁止用旧上下文直接重试，要求重新添加引用并发送新任务。原始通过记录是修复前证据，不代替最终门禁。

随后完整 CI 的命令行阶段出现三项失败：两项真实 SDK 本地夹具遭遇 Windows 端口 `EACCES`，另一项 200,000 字符长粘贴暴露旧脱敏赋值扫描的二次复杂度，最终超时。保留失败输出，不放宽资源取消或会话终态断言。离线服务只对模型请求前的端口绑定增加 Windows 保留端口重试，持续失败仍在十六次后拒绝；真实提供商请求仍为零。

脱敏扫描改为每个名字只检查一次分隔符，保留值扫描及流式尾部保护。1,296 种赋值／引号／命令前缀的前后比较没有输出差异；原扫描 1,000／4,000／16,000 字符约 1／16／259 ms，新扫描 256 KiB 约 0.4 ms（本机单次诊断，不作跨机器性能保证）。新增大文本末尾秘密及持续端口拒绝回归；相关五文件 33 项定向测试通过。最终完整门禁仍另行记录，不能用此定向结果替代。

下一轮命令行完整阶段通过 64 文件／437 项 Vitest 及 SDK 冒烟，窗口阶段主动中断以补齐新发现的取消问题，不能记作完整 CI 通过。正确指向隔离 daemon 的延迟回归在修复前证实：关闭保存中的引用对话框后仍加入一项引用。关闭／卸载现在同步取消该草稿附加动作，代码选区沿用同一取消信号；已创建的宿主未绑定副本仍按容量和七天保留规则处理，不删除历史或取消 SDK 后台任务。

首次取消测试的页面级延迟路由绕过夹具转发、收到其他开发实例的拒绝响应，修正后才建立上述失败证据。八项引用的新增窄窗回归又发现固定高度列表遮住发送栏；列表上限改为 `min(10rem, 15dvh)`。八项可修改／第九项拒绝、引用取消及选区取消三项实际 Electron 定向回归通过；收起配置时发送按钮直接可见，明确展开配置时沿用可滚动输入区。这些结果不替代最终完整门禁和原生验收。
